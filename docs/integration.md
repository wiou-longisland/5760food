# 与现有知食项目衔接

## 当前交付范围

独立 React + TypeScript + Vite 模块；参考 5760Project.docx 的视觉规范，未访问同学线上服务、未修改其数据、未创建真实账号。当前状态切换在 App 内完成，不使用生产 URL 路由。

整合时复用既有 header、Supabase Auth 会话及 user ID；合并进现有前端入口，不要替换现有 worker、SQL 或认证实现。现有 CSS 和本模块含全局样式，整合前需将社区样式限定在模块容器内，或迁移到 CSS Modules，避免影响已有页面。

## 组件和文件

- `src/main.tsx`：App（列表、详情、个人列表）、Photo（图像）、Publish（发布表单）。
- `src/data.ts`：示例数据与 Recipe / Ingredient 类型。
- `src/style.css`：桌面和手机样式。
- `public/images/`：两张 AI 合成的六宫格素材，CSS 显示对应菜品区域。
- `tests/community.spec.ts`：浏览器行为验证。

## 真实 API 设计（未实现）

浏览器 → Cloudflare Workers → 外部服务。密钥在服务端配置；不写入前端或仓库。

1. 图片：浏览器申请上传签名 → Workers 校验身份、文件约束 → Cloudinary 上传 → 返回图片资源标识 → 发帖时关联资源。服务端验证上传资源归属，不能只相信浏览器提交的地址；处理未发布图片的清理。
2. 营养：食材名称检索 USDA 候选 → 用户确认 FDC ID、生熟状态与单位 → 后端按克重汇总 → 除以份数 → 返回数值、单位、来源 ID、缺失项及估算时间。份数只影响食材总量展示，不改变同一配方的每份营养。
3. 标签：食谱标题、已确认食材与步骤 → Workers → DeepSeek → 结构校验 → 候选标签 → 用户确认。营养标签由明确规则生成；模型不能给出过敏安全保证。
4. 发布：保存已确认食谱、食材、步骤、图片引用、标签、营养来源和状态。作者由验证后的会话确定。
5. 点赞/收藏：自建接口维护用户和帖子的关联；唯一约束 `(user_id, recipe_id)` 防止重复。社区公开展示食谱；用户健康档案不随帖子发布。

建议接口：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | /api/recipes | 分页搜索、标签筛选和排序 |
| POST | /api/recipes | 创建食谱 |
| GET | /api/recipes/:id | 查看详情 |
| PUT / DELETE | /api/recipes/:id/like | 点赞和取消 |
| PUT / DELETE | /api/recipes/:id/bookmark | 收藏和取消 |
| POST | /api/recipe-nutrition | 查询、计算营养 |
| POST | /api/recipe-tags | 获取候选标签 |
| POST | /api/image-upload-signature | 申请受控图片上传 |

以上自建接口不计作课程要求的不同来源第三方 Web API。全项目复用同一外部服务只算一个来源。

## 数据缺失与错误

保留未填写、未匹配和明确不存在之间的区别。无法把“个”“勺”可靠换算成克时需确认换算依据。缺失营养不能记零；原型中新增食谱的内部数值占位不会展示成营养结论，真实后端应改用 nullable 营养字段与 completeness 状态。

区分查询失败、无匹配、部分匹配、完整结果。API 失败不应删除草稿。生产中需加入服务端校验、频率限制、请求超时、可控重试、内容举报与审核、图片限制和作者编辑/删除权限。此类服务端能力不属于当前 mockup 的已实现功能。

## 第二版：两个页面的连续性与真实档案接入

本版入口：社区 `/#/` → 卡片点击 → `/#/recipe/:id` → 返回社区。筛选和排序在本次页面会话内保留；刷新详情仍可直达；点赞、收藏和虚拟档案选择持久保存。当前版本仅桌面（最小宽 1040px），不另做手机端页面。

真实衔接时：

1. 将本模块放进 dietary-profile 的 React 入口和路由，复用顶部品牌及已有 Supabase 会话，替换虚拟 profile-trigger；本模块 CSS 仍需限定作用域。
2. 通过同站点 Workers 用户接口读取用户已经确认的档案，不从社区 URL 接受任意 userId。若独立部署，不假设账号会话可跨域自动共享；优先整合同站点，否则要明确 CORS、令牌验证与会话刷新策略。
3. 写一个明确的适配器，把真实输出的过敏、硬性排除、软偏好与 unknown/none/provided/uncertain 转成本模块使用的比较条件。真实字段路径以 shared/contract.d.ts 和同学提供的 JSON 样例为准，本版未获取这些源码，不声称已完成适配。
4. 通过共同食材编号及别名表匹配真实配料，不能只靠中文名称片段。疾病名称不能直接转成禁食项。资料未知时展示待确认，不显示安全结论。
5. 当前 matchRecipe 的规则只用于虚拟案例：鱼类、奶类、肉类等已知项与示例食材对照。综合推荐把冲突食谱排到最后，不自动删除；用户可选择隐藏。真实过敏匹配与排序应在后端执行，返回 conflictReasons、unresolvedItems、preferenceMatches、profileVersion，便于解释和复核。
6. 真实收藏/点赞使用原有登录用户 ID 写入 D1，替代 localStorage；周榜由带时间戳的收藏事件按明确时区和周边界聚合。上周统计固定快照，不能用全部历史收藏代替。

目前页面的五组营养标签为手工虚拟示例。正式版本应为每个标签保存来源（作者/AI建议/规则）、证据和审核状态；低盐低糖等需要明确阈值与完整数据，无麸质/无乳制品不能由“未看见相关配料”推断安全。

## 不合并代码时如何完成课程报告

可以独立展示两个模块，使用同一个虚拟用户和一致的 JSON 样例串联：同学确认档案 → 导出确认结果 → 社区适配器读取档案 → 冲突后置与说明。报告必须注明“接口设计/模拟演示，未完成实时联调”，不要写成已共享真实账号与数据库。这样保留完整产品流程，也准确反映实现边界。

## 第三版：发布向导（已实现本地原型）

新增 `/#/publish`：基本信息与图片 → 食材匹配 → 烹饪步骤 → 营养与标签 → 发布预览。现在可演示发布闭环，不再仅依赖报告描述。原型没有服务端上传、认证或数据库写入。

- `src/Publish.tsx`：五步校验、最多六张图片、本地压缩、封面选择、食材候选确认、未知匹配、克重确认、增删/调整步骤、示例营养计算、五组标签确认与发布。
- `src/publish.css`：沿用知食桌面布局和配色。
- 草稿：localStorage 的 `zhishi-publish-draft-v3`，自动保存；空间不足显示未保存。发布成功才移除草稿。
- 发布帖子：`zhishi-posts-v3`；只有成功写入本地存储后才跳到详情。刷新后仍可从社区、搜索和收藏进入。其他设备看不到这些本地帖子。
- 模拟食材目录不含真实 FDC ID，不调用 USDA。单位为 g 时直接计算；ml、个、勺必须由用户提供可食部克重，否则营养待补全。任一食材未匹配/未换算时，整体营养显示待补全，不显示部分和冒充完整值。
- 标签建议使用本地确定性规则，不调用 DeepSeek；饮食需求标签由作者选择并明确标注未验证。图片只保存本地，不调用 Cloudinary。
- 后续可用相同页面状态接入前述 Worker 接口，用真实候选、来源、缺失信息和上传资源标识替换本地 fixture；校验、身份鉴别、营养与标签规则还须在后端重复执行。

报告状态应更新为“已完成可交互发布页与本地发布演示，真实 API 与云端发布尚未实现”。
